# Architecture

Evidence for every number below: [profile.md](profile.md) (generated by `npm run profile`) and [verify.md](verify.md) (generated by `npm run verify`).

## 1. Source shape

- Each raw doc is one **API response envelope** from provider **`xbyte`**: `endpoint`, `params`, `payload` (`request_log` + data), `statusCode`, `createdAt`/`updatedAt`.
- `domain` = **platform** (`talabat` in every doc).
- There are three collections, which form a crawl chain:

| Collection | One doc = | Data in | Docs |
| --- | --- | --- | --- |
| `xbyte-raw-locations` | full area list | `payload.results[]` `{location_id, location_name, location_slug}` | 8 |
| `xbyte-raw-restaurants` | one listing page for one area (`params.areaId`, `areaSlug`, `page_no`) | `payload.results[]` `{area_name, restaurant_name, restaurant_url}` | 70 |
| `xbyte-raw-menus` | one restaurant page (`params.restaurant_url`) | `payload.results[0]` restaurant + `category[].items[]` | 500 |

- Flow: **locations → restaurants listing (per area, paginated) → menus (per restaurant page)**.

## 2. Anomalies

### Locations
- 8 identical snapshots of the same 697 areas (5,576 rows → 697 distinct `location_id`).
- `location_slug` is not unique: 685 slugs for 697 ids, and **11 slugs are ambiguous** (`industrial-area` → 3 ids).
- `location_name` is duplicated too: 686 distinct names after normalization.
- Whitespace issues: `1594 "Al  Muntazah"` has a double space.

### Restaurants listing
- `params.areaId` is a **string** (`"1468"`), while `location_id` is an **int**.
- Repeated page fetches: 70 docs but only 33 distinct `requests_url`.
- **463 distinct URLs but 302 restaurants.** The URL is unstable because `?aid=` changes per area, and the stable id is embedded in the path (`/restaurant/{id}/`).
- **161 restaurants are listed in both areas**, so restaurant ↔ area is many-to-many.
- 2 docs are provider errors (both `statusCode` 200):
  - `page_no` 3: `payload.Page Error Message: "Page limit exceeded."` with `results: []`;
  - `page_no` 14: only `payload.error: ""`, no `results`.

### Menus
- **155 of 500 are soft failures**: `statusCode` 200, but the payload contains only `Message: "This is not restaurant page (Talabat)."`.
- `payload.results` always has length 1.
- Numbers stored as strings: `latitude`, `longitude`, `deliveryFee` (all 345).
- `DeliveryTime` is free text: `"25-40 mins"`, `"30 mins"`.
- Mixed int/double: `rate` (314 double / 31 int) and item `price` (27,322 int / 3,780 double).
- Field naming is inconsistent: `Minimum Order`, `Restaurant Address` (spaces), `DeliveryTime`, `City` (Pascal), `totalReviews` (camel), `category_id` (snake).
- `Contact` is always the placeholder `"00000-00000"`.
- `totalReviews` is **always 0** (345/345).
- Item `rating` is 0 in **92.6%** of items (28,798 / 31,102).
- Blank item `description` in 2,071 items; null `image` in 1,631.
- 16 restaurants have an empty `category[]`, i.e. no menu.
- `Restaurant Address` matches no `location_name` in 31 of 345 cases (14 values, e.g. `"Jumeirah"`, `"Dubai"`, `""`).

### Items and categories
- **2,266 `item_id`s repeat within the same restaurant**, across different categories, and never across restaurants. They come from promotional categories: "Picks for you 🔥" (1,473 occurrences) and "Offers" (856). Every repeat is **identical** in `price`, `item_name`, `description`, `image` and `rating` (verify §9: 0 of 2,266 groups differ), so there is no promo pricing.
- **`category_id` is not unique within a restaurant**: 60 ids are reused with different names (e.g. `"Offers"` + `"Combos"`), and all of these are within one restaurant.

### Cross-collection
- The listing and the menus share **zero** restaurants in this sample (302 vs 500 ids).
- `results[0].outletCode` = id from the URL in 345/345 menus; `results[0].id` = id from the URL in 0/345.
- `results[].id` is unique per outlet (345 ids for 345 outlets), so there's no evidence it's a brand id.

### Time
- `payload.request_log.request_time` has **no timezone** (`"2026-07-22 01:11:54.856135"`, about 7h behind `createdAt`).
- `createdAt` (a BSON date in UTC) is therefore used as **`fetchedAt`**.

## 3. Target model

- `areas` and `menu_items` each have one source, so they carry `source: { provider, platform, rawId, fetchedAt }`.
- `restaurants` has two sources, and each one gets its own freshness record (see [Conflict rule](#conflict-rule)).

### `areas`
| Field | From |
| --- | --- |
| **key** `{provider, platform, externalId}` | `externalId` = `location_id` |
| `name` | `location_name`, whitespace-normalized (trim + collapse spaces) |
| `slug` | `location_slug` (not unique, not a key) |

### `restaurants`
- **Key:** `{provider, platform, externalId}`, where `externalId` = the id from the URL (= `outletCode`).
- Field ownership is split by source, so each source only writes its own fields:

| Source | Owns |
| --- | --- |
| Listing | `sources.listing {rawId, fetchedAt, name}`, `url`, `areaIds` (`$addToSet`) |
| Menu | `sources.menu {rawId, fetchedAt, name}`, `logo`, `platformInternalId` (`results[0].id`), `location` (GeoJSON Point `[lng, lat]`), `rating`, `ratingsCount`, `deliveryFee`, `deliveryTime {min, max}`, `minimumOrder`, `city`, `addressText`, `categories[]` |

- **`name` is derived, not owned:** `name = sources.menu.name ?? sources.listing.name`. Each write recomputes it with `$ifNull` in the same update pipeline. It depends only on stored state, not on which write ran last.
- **`url` is canonical:** the query string is stripped (`?aid=` changes per area). This gives `https://www.talabat.com/uae/restaurant/{id}/{slug}`.
- `categories[]` is embedded, with fields `{key, categoryId, name, position}`.
- **Category key** = `categoryId` + normalized name, because `category_id` alone is not unique within a restaurant.

### `menu_items`
| Field | From |
| --- | --- |
| **key** `{provider, platform, restaurantExternalId, externalId}` | `externalId` = `item_id` |
| `name` | `item_name` |
| `description` | blank → `null` |
| `price` | number |
| `image` | as-is (nullable) |
| `rating` | `0` → `null` |
| `categoryKeys[]` | every category the item appears in (merges the 2,266 promo duplicates) |

- **Repeated item:** the first occurrence in category order supplies the fields. The repeats are identical today (verify §9), so this rule never changes the result. It's there so the choice is deterministic if they ever differ.

### Conflict rule
- **Per source: newest `fetchedAt` wins; ties are broken by the larger raw `_id`.**
- `restaurants` keeps one freshness record per source:
  ```
  sources: {
    listing: { rawId, fetchedAt, name },
    menu:    { rawId, fetchedAt, name }
  }
  ```
- A write compares only against **its own** source's record. A listing fetch (Sep) can't block menu fields fetched earlier (Jul), and the reverse also holds.
- **Exception:** `areaIds` uses `$addToSet` without a freshness check. A set union gives the same result in any order, so a guard isn't needed.
- Result: the same raw data gives the same target regardless of job order or retries.

### Operational collections
- `runs`: one doc per run: `status`, `counters` (read / transformed / written / skipped / failed), per-stage counters, `jobs {total, done, failed}`, `dispatchCursor`, timings, `error`. It also holds `finishedJobIds`, which makes job completion idempotent (see [Queue topology](#8-queue-topology)).
- `quarantine`: every rejected raw doc or record, with `runId`, `jobId`, `collection`, `rawId`, `entity`, `recordIndex`, `stage`, `reason` and `createdAt`. Nothing is dropped silently.

## 4. Indexes

| Collection | Index | Why |
| --- | --- | --- |
| `areas` | unique `{provider, platform, externalId}` | upsert key, idempotency |
| `restaurants` | unique `{provider, platform, externalId}` | upsert key, idempotency |
| `restaurants` | `{areaIds: 1}` (multikey) | "restaurants in area X" |
| `restaurants` | `{location: "2dsphere"}` | geo queries (near / within) |
| `menu_items` | unique `{provider, platform, restaurantExternalId, externalId}` | upsert key, idempotency |
| `menu_items` | `{restaurantExternalId: 1, categoryKeys: 1}` | "menu of restaurant X", "items in category Y" |
| `quarantine` | unique `{runId, collection, rawId, entity, recordIndex, stage}` | a retried job upserts the same entry instead of duplicating it |
| `quarantine` | `{runId: 1, createdAt: 1}` | `GET /runs/:id/errors`, in order |

All indexes are created on boot (`MongoTargetWriter.onModuleInit`, `MongoQuarantineRepository.onModuleInit`). Nothing is created in the raw DB.

## 5. Trade-offs

| Decision | Why | Cost |
| --- | --- | --- |
| Categories **embedded** in restaurants | small (max 38 per restaurant), bounded, no lifecycle of their own, always read with the restaurant | can't query categories across restaurants cheaply |
| Items as a **separate collection** | large (31k rows, up to 214 per category), queried independently, upserted per item | a menu read needs a second query |
| `areaIds` **embedded** array vs a join collection | many-to-many but small per restaurant; `$addToSet` stays idempotent; multikey index covers lookups | no per-link metadata (e.g. first seen) |
| `addressText` **not linked** to areas | names are ambiguous (11 slugs, 686 names for 697 ids) and 31/345 addresses match nothing | no area for menu-only restaurants |
| **No `brands` collection** | `results[].id` is unique per outlet, so there's no evidence it's a brand | add one later if chain data appears |
| `totalReviews` **dropped** | always 0, so it carries no information | — |
| Item `rating` 0 → `null` | 92.6% are 0, which means "unrated", not "rated zero" | a genuine 0 rating is indistinguishable |

## 6. Known gaps

- **Items removed from a menu stay in the DB.** Upserts never delete, so an item that disappears in a newer menu fetch keeps its old row. A future fix is a `lastSeenAt` per item (or a soft delete for items not seen in the latest menu fetch). This is not built now.
  - Embedded `categories[]` don't have this problem, because a newer menu replaces the whole array.

## 7. Pipeline stages

One batch job runs one fixed `_id` range of one raw collection through these stages:

```
raw docs ─► validate ─► extract ─► normalise ─► map ─► deduplicate ─► project ─► write
            (envelope)  (fan-out)  (per record)  (per record) (per batch)  (per entity)
            └──────────────────── pure: runBatch() in src/core ─────────────────────┘  └ I/O ┘
```

| Stage | Input → output | What it does | On failure |
| --- | --- | --- | --- |
| validate | raw doc → envelope | Zod schema from the adapter: envelope structure, `domain`, `statusCode`, known provider failures (soft failures, page errors) | whole doc quarantined |
| extract | envelope → records | adapter function: one envelope → N records per output (a menu → 1 restaurant + N items) | doc quarantined for that output (a throw is caught) |
| normalise | record → values | for each mapped field: read the source path, trim (blank → `null`), apply its transforms (`toNumber`, `parseDeliveryTime`, ...) | record quarantined with the field and reason |
| map | values → entity | assemble the target entity; a required field that is missing/empty fails | record quarantined |
| deduplicate | entities → entities | one survivor per (entity, source slot, natural key) **across the batch**: newest `fetchedAt` wins, tie → larger rawId; within the winning envelope the first occurrence wins and `unionOnMerge` fields (`categoryKeys`) are unioned; `addToSet` fields (`areaIds`) are unioned across all | never fails (merges are visible as `in` − `out`) |
| project | entity → `EntityUpsert` | add `provider`/`platform` to the key, split owned fields / `addToSet` / `derived`, attach the source record | entity quarantined (empty key) |
| write | upserts → target | `TargetWriter` (see [Conflict rule](#conflict-rule)); then quarantine entries and counters are written | throws → job retried |

- **Pure:** validate → project is one pure function (`runBatch`): no I/O, no clock, no randomness. The same docs give the same upserts, failures and counters (unit-tested).
- **Seam:** the stages are generic. The provider supplies only declarations: schema, `extract`, field mapping with transforms, natural key, and merge/slot/derived options.
- **Counters:** every stage reports `in / out / failed`. They are added to the run atomically with the job's completion.

## 8. Queue topology

```
POST /runs ──► runs: status=queued
     │
     └─► factory-batches  "dispatch"  jobId dispatch-<runId>
              │  DispatcherService: per source collection, scan _ids only,
              │  cut ranges of BATCH_SIZE, save dispatchCursor after each enqueue,
              │  finally setJobsTotal
              ▼
         factory-batches  "batch"  jobId <runId>:<collection>:<batchNo>
              │  data: (afterId, untilId] range ; concurrency = WORKER_CONCURRENCY
              │  BatchService: read range ─► runBatch ─► TargetWriter ─► quarantine ─► completeJob
              │
              ├─ bad document ─► quarantine, job still succeeds
              ├─ infrastructure error (throw) ─► retry: 5 attempts, exponential backoff 1s·2s·4s·8s
              └─ attempts exhausted / UnrecoverableError
                       ▼
                 factory-batches-dlq  (job data + failedReason)  ;  run.jobs.failed++
```

- **One queue, two job names.** Dispatching is a job too, so `POST /runs` returns `202` at once, and a crashed dispatch is retried like any other job.
- **Range jobs.** A job owns `(afterId, untilId]` of one collection, at most `BATCH_SIZE` docs. Its id is deterministic (`batchNo` counts across the run), so re-enqueuing the same range is deduplicated by BullMQ. Completed jobs are kept so that deduplication still works.
- **Retry vs quarantine.**
  - Bad data never throws: it is a stage failure and goes to quarantine.
  - Anything that throws is infrastructure (Mongo/Redis down, unknown entity type) and is retried.
  - `UnrecoverableError` (unknown run or job name) skips the retries.
- **Dead letters.** On the final failure the `failed` worker event copies the job to `factory-batches-dlq` with the reason. For a batch it records `jobs.failed` on the run; for a dispatch it marks the run `failed`.
- **Completion.** `completeJob` is one atomic update:
  - it `$inc`s `jobs.done|failed` and all counters;
  - it sets `status: completed` once `done + failed == total`;
  - its filter `finishedJobIds ≠ jobId` applies each job at most once.

  `jobs.total` stays `null` until the dispatcher has enqueued everything. `setJobsTotal` then runs the same completion check, in case every job already finished.
- **Resume after a crash.**
  - Dispatcher: continues from `dispatchCursor` with the same batch numbers, so the same job ids.
  - A batch killed mid-job: BullMQ's stall detection (≈30 s) puts it back in the queue. It re-reads the same range. Writes and quarantine entries are idempotent upserts, and counters are applied once per job.

  Verified by killing the worker with `kill -9` mid-run (58 jobs) and by the integration test.
